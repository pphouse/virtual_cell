# 提出とログインの手順 — 別のチャット・別のコンテナで続けるために

`docs/09` は**何を考えたか**の引き継ぎ。この文書は**どう動かすか**の引き継ぎ。
新しいセッションで「ログインして提出する」までを、ここだけ見てできるようにしてある。

> **このリポジトリは public。** API トークンそのものを、この文書にも、
> コードにも、コミットメッセージにも、PR 本文にも**書かない**。
> 置き場所と渡し方だけを書く。

---

## 0. 前提 — コンテナは残らない

リモート実行のコンテナは数時間おきに作り直される。**生き残るのは git の中身だけ。**
実際に 2026-09-07 → 10-05 の間で `.venv` / `.venv-cli` / `.venv-eval` /
`data/` / scratchpad（トークン・ライブラリ・参照データ・提出物）が**全部消えた**。

だから新しいチャットでやることは常に同じ 4 ステップ:

1. venv を 3 つ作る（§2）
2. トークンを scratchpad に置き直す（§1）
3. データを取り直す（§3）— 一番時間がかかる。約 1.5 GB・30〜60 分
4. ビルド → 検証 → 提出（§4〜§6）

## 1. 認証情報

### 1.1 どこから取るか

チャレンジのアカウントページで発行する **personal access token**（`vcc_pat_` で始まる）。
エンドポイントは `https://virtualcellchallenge.org`。

### 1.2 どこに置くか

```bash
SP=<このセッションの scratchpad>      # 例: /tmp/claude-.../scratchpad
printf '%s' '<token>' > $SP/vcc_token   # 改行を入れない
chmod 600 $SP/vcc_token
```

scratchpad は git の外にあり、`.gitignore` ではなく**リポジトリの外**なので
誤コミットの経路が無い。`data/` や `outputs/` に置かないこと（gitignore 頼みになる）。

### 1.3 どう渡すか

**ヘッドレス環境では `vcc login` を使わない。** keyring が無く、対話プロンプトで止まる。
コマンドごとに環境変数で渡す:

```bash
VCC_TOKEN=$(cat $SP/vcc_token) .venv-cli/bin/vcc --json whoami
```

`export` して長く残すより、1 行ずつ付けるほうが安全（ログに環境が載る事故を減らせる）。
**`echo $VCC_TOKEN` や `cat $SP/vcc_token` を単体で実行しないこと**——
出力はそのままチャットの文脈に残り、その文脈は人間が読める場所に行く。

### 1.4 確認

```bash
VCC_TOKEN=$(cat $SP/vcc_token) .venv-cli/bin/vcc --json whoami
```

返るのは `email` / `name` / `team_id` / `approved` / `verified` / `active` /
`can_submit` / `endpoint`。

> **`can_submit: true` は「アカウントが提出資格を持つ」という意味で、
> 当日の枠が残っているという意味ではない。** 枠の残りを返す API は無い。
> 実際に `vcc submit` を叩くしかなく、枠切れなら**何もアップロードせずに**
> こう落ちるので、試すこと自体は安全:
>
> ```
> → checking your team's daily submission allowance …
> vcc: Your team has already used its submission allowance for today
>      (resets at 00:00 UTC). Nothing was uploaded.
> ```

### 1.5 ★ ローテーション

**いま使っているトークンは、2026-08 のチャット本文に平文で貼られた。**
チャットのログは残るので、**このトークンは漏洩したものとして扱うべき**。
アカウントページで**再発行して古いものを失効させ**、新しい値を §1.2 の手順で置き直すこと。
失効させても、提出済みのエントリやスコアには影響しない。

## 2. 環境

```bash
cd /home/user/virtual_cell
python3 -m venv .venv      && .venv/bin/pip install -e '.[dev]'
python3 -m venv .venv-cli  && .venv-cli/bin/pip install vcc-cli
.venv/bin/python -m pytest tests -q      # 40 件。チャレンジデータ不要
.venv/bin/ruff check .
```

**公式 CLI を別 venv に入れる理由**: 配布名 `vcc` が公式 CLI のもので、
本パッケージ `vcc2026` と衝突する（同居させると `vcc` コマンドが壊れる）。

採点用の `.venv-eval`（`cell-eval` 0.16.0 を入れる）を作る場合、
**そこに `vcc2026` は入っていないので `PYTHONPATH=src` が要る**:

```bash
python3 -m venv .venv-eval && .venv-eval/bin/pip install 'cell-eval==0.16.0'
PYTHONPATH=/home/user/virtual_cell/src .venv-eval/bin/python scripts/local_score.py ...
```

## 3. データの再取得

| もの | 置き場所 | 取り方 | サイズ |
|---|---|---|---|
| チャレンジ配布物 | `$SP/vcc` | `vcc datasets download controls -d $SP/vcc` → `unzip -o vcc_2026_controls.zip` | 632 MB |
| STRING v12 隣接行列 | `$SP/string/adj_400.npz` | `scripts/download_public_data.sh` | 6 MB |
| Replogle GWPS 疑似バルク | `$SP/replogle/` | figshare article **20029387** の `K562_gwps_raw_bulk_01.h5ad` | 375 MB |
| 署名ライブラリ | `$SP/lib_gwps300.npz` | §3.1 | — |
| DepMap 共必須性 | `$SP/depmap/coess.npz` | figshare **27993248** の `CRISPRGeneEffect.csv` → `scripts/build_coessentiality.py` | 429 MB → 75 MB |
| 遺伝子座標 | `$SP/genome/gene_pos.json` | UCSC refGene hg38 | 小 |

**`curl` には `-L` を付ける**（figshare はリダイレクトする。付け忘れて 0 バイトのファイルを掴んだ）。
**正規化済みではなく raw の疑似バルクを使う**（正規化版は対照に対して z 化され `inf` を含む）。

### 3.1 ライブラリの組み立て

```bash
# 2025 訓練データ（H1）を元に土台を作り、そこへ GWPS を足す
.venv/bin/python scripts/build_library_2025.py \
  --genes $SP/vcc/gene_names.csv \
  --source H1=<2025 検証分割 h5ad> --out $SP/lib_h1.npz

cut -d, -f1 $SP/vcc/pert_counts.csv | tail -n +2 > $SP/targets300.txt
.venv/bin/python scripts/build_library_gwps.py \
  --bulk $SP/replogle/K562_gwps_raw_bulk_01.h5ad \
  --library $SP/lib_h1.npz --line K562gwps \
  --restrict-to $SP/targets300.txt --out $SP/lib_gwps300.npz
```

**`--restrict-to` を外さないこと。** GWPS 全 9,743 標的を入れると
（標的 × 遺伝子）の行列が 15 GB に収まらず OOM し、しかもスコアは**下がる**
（限定版が +0.0322 良い、t=4.9。余分な 9,400 は近傍プールを薄めるだけ）。

## 4. 提出物のビルド（現行 = v25 構成）

**自己ベスト Overall +0.044279 を出した構成そのまま。**

```bash
SP=<scratchpad>
cd /home/user/virtual_cell
nohup .venv/bin/python scripts/predict_vcc2026.py \
  --bundle $SP/vcc --library $SP/lib_gwps300.npz \
  --n-components 200 --string-adj $SP/string/adj_400.npz \
  --margin 1.15 --top-margin 1.15 \
  --generic-lines H1,H1val,H1test,K562,K562gwps,RPE1 --generic-weight 0.0 \
  --specific-weight 1.0 --shared-shrink 1.0 \
  --min-abs-lfc 0.0 --pseudocount 1.0 --n-calls 3000 \
  --gene-positions $SP/genome/gene_pos.json --proximity-weight 20.0 \
  --call-size-gamma 0.5 --max-call-scale 3.0 \
  --features $SP/depmap/coess.npz --feature-blend 1.0 \
  --seed 0 --out $SP/sub.h5ad --vcc $SP/sub.vcc \
  > $SP/build.log 2>&1 &
```

* **約 30 分**、ピークメモリ 8 GB 程度。**単独で回すこと**（パネル評価と同時だと OOM）。
* 出力は `sub.h5ad` 4.3 GB + `sub.vcc` 4.26 GB + 設定を記録した `sub.h5ad.json`。
* **ディスクを先に空ける。** 空きが 9 GB を切ったら新規ビルドの前に整理する
  （v19 のとき tar 段で ENOSPC に当たった）。**提出済みの `.vcc` は消してよい。**
* `vcc prep` はこの環境では動かない（2.06e9 非零に対し約 16 GiB の常駐を要求、RAM 15 GB）。
  `.vcc` は `src/vcc2026/vccfile.py` が直接ストリーミング生成し、
  本物の `vcc prep` との一致を `tests/test_vcc_parity.py` が保証している。

### 4.1 提出前の検証（1 分。必ずやる）

`.vcc` は**無圧縮 tar に `pred.h5ad.zst` が 1 つ入っただけ**のもの。
中身が本当に HDF5 まで戻るかを見る:

```bash
.venv/bin/python - <<'PY'
import tarfile, zstandard as zstd
p = "<$SP>/sub.vcc"
with tarfile.open(p) as tar:
    print([m.name for m in tar.getmembers()])          # ['pred.h5ad.zst']
    f = tar.extractfile("pred.h5ad.zst")
    magic = zstd.ZstdDecompressor().stream_reader(f).read(8)
print("HDF5:", magic[:4] == b"\x89HDF")                 # True なら OK
PY
```

ビルドが途中で死んでも `.vcc` は出来てしまうことがある。
**この 1 分を省くと、壊れたファイルで枠を 1 つ失う。**

## 5. 提出

```bash
VCC_TOKEN=$(cat $SP/vcc_token) nohup .venv-cli/bin/vcc submit --wait \
  $SP/sub.vcc -m "<何を変えたか。後で自分が読む>" > $SP/submit.log 2>&1 &
```

進捗の確認:

```bash
tail -c 400 $SP/submit.log | tr '\r' '\n' | tail -2
VCC_TOKEN=$(cat $SP/vcc_token) .venv-cli/bin/vcc --json status <entry_id>
```

### 5.1 絶対にやってはいけないこと

> **`vcc submit` を `head` / `tail` にパイプしない。**
> プログレスバーの書き込みが SIGPIPE を受けてアップロードが死に、**提出枠を 1 つ失う。**
> 必ず `nohup` でログに落とし、ログを後から読む。

### 5.2 枠と所要時間

* **1 チーム 1 日 2 枠。00:00 UTC にリセット。**
* **採点に到達した提出だけが枠を消費する**（フォーマットエラー・409・枠切れは無料）。
* **同時に走らせられるのは 1 件。** 1 件目が published になってから 2 件目を出す。
* アップロード約 7〜10 分、採点 20〜60 分（`launching` が 20 分続くこともある）。
* **1 サイクル約 1 時間。** だから設定はオフラインで決める（§7）。

### 5.3 落ちたときの復旧

アップロードがコンテナ再起動やネットワークで切れたら:

```bash
VCC_TOKEN=$(cat $SP/vcc_token) nohup .venv-cli/bin/vcc submit --resume --wait \
  $SP/sub.vcc -m "<同じメッセージ>" > $SP/submit_resume.log 2>&1 &
```

**`--resume` は枠を消費しない**（v23 の 70% で落ちたアップロードで実証済み）。

## 7. 枠を使う前に手元で測る

1 日 2 枠しかないので、**手元の装置で符号を確認してから投げる**。
装置の作り方・換算率・ノイズ床は `docs/09` §3.2〜§3.3。要点だけ:

* **H1 排出**が本番 Overall の代理（`local_score.py` の `sum_scaled/6`）。1 腕 ≒ 17 分。
* **K562/RPE1 パネル**は `pds` 専用で 1 腕 5 分。**`nmae` には使わない**（本番と逆を指す）。
* **必ず同一シードで対を取り、2 シードで符号が一致してから枠を使う。**
  片シードの山は 4 回外した。

## 8. 困ったときの対応表

| 症状 | 原因と対処 |
|---|---|
| `vcc` が見つからない / import が壊れる | `vcc2026` と同じ venv に入れた。`.venv-cli` を作り直す |
| `vcc login` が止まる | ヘッドレスに keyring が無い。`VCC_TOKEN=...` で渡す（§1.3） |
| `Nothing was uploaded` + `allowance` | 当日の枠切れ。00:00 UTC まで待つ。枠は減っていない |
| アップロードが 70% で止まる | コンテナ再起動。`--resume --wait`（枠は減らない） |
| 提出直後に `vcc submit` が無反応で終わる | `head`/`tail` にパイプした。§5.1 |
| ビルドが exit 137 | OOM。`--restrict-to` の無いライブラリか、パネルと同時実行 |
| tar 段で ENOSPC | ディスク。提出済み `.vcc` を消す。`.tmp.zst` が残っていれば再 tar できる |
| `local_score.py` が「no target in common」 | DE 真値と参照が別分割。`local_reference_de.py --adata <参照>` で作り直す |
| `.venv-eval` で `ModuleNotFoundError: vcc2026` | `PYTHONPATH=/home/user/virtual_cell/src` |
| figshare から 0 バイト | `curl` に `-L` が無い |

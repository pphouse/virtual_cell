# 実測でわかったこと

推測ではなく、実データとリーダーボードで測った結果だけを置く。
再現に使ったスクリプトを各項に記す。

## 1. リーダーボード初回提出（2026-08-24）

`entry 6tR2DLbUuOmLxUgmRCgO` — **on-target ノックダウンのみ**（トランス項なし）。
どの指標が on-target 項だけでいくら取れるかを、汚さずに測るための提出。

| 指標 | scaled | 生値 |
|---|---|---|
| Overall | **−0.0638** | (Rank 130) |
| Perturbation discrimination `pds` | +0.0118 | `pds_cosine` 0.5057 |
| Expression accuracy `mse` | 0 | `expr_mse_unbiased_capped_norm` 1.0980 |
| DE log-FC accuracy `nmae` | +0.0033 | `de_wilcoxon_lfc_nmae` 0.9993 |
| **DE direction fidelity `fid`** | **−0.3419** | `..._direction_fidelity_yield_raw` 0.4097 |
| DE direction reach `reach` | −0.0183 | `..._direction_reach_raw` 0.0631 |
| DE significance overlap `jac` | −0.0374 | `de_wilcoxon_sig_jaccard` 0.0165 |

読み取れること:

- **`pds_cosine` = 0.5057 は偶然と同じ。** on-target 項は摂動の識別に一切
  寄与しない。標的遺伝子はどの摂動でも違うのに識別できないということは、
  この指標がトランス署名で決まっていることを意味する。**pds のレンジは
  ほぼ丸ごと手つかず** — 最大の伸びしろ。
- **損失はほぼ全て `fid` に集中。** 生値 0.41 で、ベースラインは約 0.51
  （scaled 0 の定義から逆算）。つまり **予測方向が偶然より悪い**。
  非標的の予測はノイズのはずなので、これはモデルではなく排出モデルの問題だと
  当たりがついた（→ §2）。

## 2. 排出モデルが偽の DE を撒いていた（最大の発見）

`scripts/null_emission_test.py`

摂動を一切かけない（fold change = 0）状態で細胞を排出し、
同じ文脈の実コントロール細胞に対して採点側と同じ Wilcoxon 検定をかける。
忠実な排出なら有意遺伝子はほぼ 0 になるはず。

| 排出方式 | 有意遺伝子（11,658 中） | 向き |
|---|---|---|
| 実細胞（真の null） | **0** | — |
| 全遺伝子リサンプル a=0.0 | 5,705 (49%) | 99.8% が DOWN |
| 全遺伝子リサンプル a=0.5 | 82 | 57% が up |
| **全遺伝子リサンプル a=1.0（初回提出）** | **93** | **89% が UP** |
| 全遺伝子リサンプル a=2.0 | 160 | 94% が up |
| **予測した遺伝子のみ更新（修正後）** | **0** | — |
| 修正後 + 1 遺伝子ノックダウン | **1**（その遺伝子だけ、DOWN） | — |

初回提出は、**摂動を予測していない遺伝子に対して、
全 300 摂動 × 3 文脈で同じ向きの偽 DE を約 93 個ずつ**渡していた。
実際のノックダウン応答は down が優勢なので、これだけで方向一致率が
偶然を下回る。`fid = −0.34` の正体。

### なぜ較正をすり抜けたか

排出モデルの平滑化パラメータは当初、**遺伝子ごとの分散と検出率**が
実コントロール細胞と一致するように較正していた。a=1.0 で分散比 0.992、
検出率比 0.992 — どちらも 1% 以内で一致していた。**それでも間違っていた。**

採点側が回すのは Wilcoxon 順位検定で、これは分布の 2 次までではなく
**分布の形そのもの**を見る。2 つのモーメントを合わせても、形は合わない。

正しい較正基準は「実データと見分けがつかないこと」ではなく
**「予測がゼロなら排出は恒等写像であること」**。今の実装は構成上これを満たす:
予測が非ゼロの遺伝子だけを再抽出し、残りは実コントロール細胞をそのまま通す。
較正ではなく構造で保証されるので、以後この失敗は起きない。

## 3. ノックダウンが半分しか効いていなかった

同じ排出モデルに 2 つ目のバグ。平滑化の擬似カウントを
掛け算の**前に両側へ**足していたため、ノックダウンが希釈されていた:

```
誤: lam = (counts + a·L·m) · fc     → fc=0.15 のつもりが実際は 0.30
正: lam = counts · fc + a·L·m · max(fc−1, 0)
```

擬似カウントの目的は「その細胞でゼロの遺伝子も**上げられる**ようにする」こと
なので、上げる側にだけ効かせるのが正しい。初回提出の実測 on-target
log fold change は −0.84〜−1.15（意図は −1.20）で、この希釈と一致していた。

## 4. CRISPRi ノックダウンの実効率

`scripts/validate_on_2025.py` — 2025 公開データ（H1 hESC）の実測 150 標的。

| | 値 |
|---|---|
| 標的遺伝子の残存発現率（中央値） | **0.148** |
| 四分位範囲 | 0.095 – 0.234 |
| 下がった標的の割合 | **150/150 = 100%** |

文献値から置いていた 0.30 は 2 倍高すぎた。0.15 に修正。

## 5. コントロール細胞の共発現は、トランス応答を予測しない

同じ 150 標的で 2 通り測った。**どちらも信号ゼロ。**

**(a) 共発現が直接トランス応答を予測するか**（`validate_on_2025.py`）

| | 値 |
|---|---|
| 予測 vs 実測トランス応答の相関（平均） | **−0.003** |
| 中央値 | −0.011 |
| 正の相関だった摂動の割合 | **44.7%**（偶然以下） |
| 効果量が大きい上位 1/4 に限っても | −0.008 |

**(b) 共発現が「署名の似ている遺伝子」を当てられるか**（`validate_knn_2025.py`）

150 標的を 1 つずつ leave-one-out し、残り 149 の実測署名を
類似度で重み付け平均して予測する。標的遺伝子自身は採点から除外。

| 予測子 | 平均 r | discrimination |
|---|---|---|
| 共発現 kNN | 0.165 | 0.509 |
| **平均署名（全摂動の平均を出すだけ）** | **0.188** | 0.500 |
| STRING kNN | **0.235** | **0.584** |
| oracle kNN（真の署名類似度・使用不可） | 0.471 | 0.748 |

読み取れること:

- **共発現 kNN は「平均署名を出すだけ」に負ける。** discrimination は 0.509 で
  ほぼ偶然。コントロール細胞の共発現には、どのノックダウンが似ているかの
  情報が入っていない。
- **モデルの形は悪くない。** oracle が r=0.471 / discrimination 0.748 に届くので、
  「測定済み署名の類似度重み付き平均」という枠組み自体は十分機能する。
  **ボトルネックは遺伝子表現。**
- **STRING（機能的相互作用ネットワーク）は本物の改善。** r 0.188→0.235、
  discrimination 0.500→0.584。GPU も学習も不要で、遺伝子カバー率 98.5%。
  ただし oracle の 0.748 にはまだ遠い。

2025 の上位陣が揃って「タンパク質埋め込みが効いた」と報告しているのは
この同じ穴を埋めていたからだと考えられる。次の投資先は遺伝子表現。

## 6. 転移元データの制約

| | 値 |
|---|---|
| 2025 公開データの遺伝子と 2026 の重なり | 18,077 / 18,533 |
| 2025 で摂動された標的と 2026 の 300 標的の重なり | **13 / 300** |

つまり **287/300 は直接転移できず、類似度による外挿に頼る**。
§5 の結論がそのまま効いてくる。

## 7. 環境上の制約（実測）

| | 値 |
|---|---|
| 提出物の stored entries | 2,059,467,763（上限の 43.4%） |
| 1 細胞あたり | 5,721（実コントロール細胞は 5,973） |
| 生 CSR としてのサイズ | 約 17 GB |
| gzip 圧縮後の h5ad | 4.30 GB |
| `.vcc` | 4.24 GB |
| `vcc prep` が必要とする常駐メモリ | **約 16 GiB**（CLI 自身の `sizing.py` の実測値） |
| この環境の RAM | 15 GB |

`vcc prep` はこの環境では動かない。密度を下げれば動くが、それは
実コントロール細胞より浅い細胞を出すことを意味し、DE の検出力を
ローカルの都合で捨てることになる。そこで `.vcc` を直接書き出し、
**本物の `vcc prep` との一致をテストで保証**している
（`tests/test_vcc_parity.py`: 小規模な提出物を両方の経路に通し、
アーカイブから戻る AnnData が一致することを確認）。
